# Cocke-Younger-Kasami (CYK) Parsing Algorithm

## Introduction

The Cocke-Younger-Kasami (CYK) algorithm is a dynamic programming algorithm used for parsing context-free grammars (CFGs). It determines whether a given string can be generated by a given CFG. The algorithm is particularly efficient when the grammar is in Chomsky Normal Form (CNF), which simplifies the structure of production rules. This implementation specifically targets grammars in CNF.

**When to use it:**

*   To check if a string belongs to the language defined by a CFG.
*   To build a parse tree for a valid string.
*   When the grammar is guaranteed to be in Chomsky Normal Form.

## Usage

Here's a C# example demonstrating how to use the `CykParser`:

```csharp
using System;
using System.Collections.Generic;

public class Example
{
    public static void Main(string[] args)
    {
        // Define a grammar in Chomsky Normal Form (CNF)
        // Example: S -> AB | a
        //          A -> BB | b
        //          B -> AB | a
        var rules = new List<CnfRule>
        {
            new CnfRule("S", "AB"),
            new CnfRule("S", "a"),
            new CnfRule("A", "BB"),
            new CnfRule("A", "b"),
            new CnfRule("B", "AB"),
            new CnfRule("B", "a")
        };
        var grammar = new CnfGrammar(rules, "S");

        var parser = new CykParser(grammar);

        // Test case 1: A valid string
        var tokens1 = new List<string> { "a", "b", "a" };
        bool canParse1 = parser.Parse(tokens1);
        Console.WriteLine($"Can parse 'ab'a': {canParse1}"); // Expected: True

        if (canParse1)
        {
            var parseTree1 = parser.GetParseTree(tokens1);
            Console.WriteLine($"Parse Tree 1: {parseTree1}");
            // Example output might look like: S(A(b), B(a))
        }

        // Test case 2: An invalid string
        var tokens2 = new List<string> { "a", "a", "b" };
        bool canParse2 = parser.Parse(tokens2);
        Console.WriteLine($"Can parse 'aab': {canParse2}"); // Expected: False

        // Test case 3: Another valid string
        var tokens3 = new List<string> { "a", "a" };
        bool canParse3 = parser.Parse(tokens3);
        Console.WriteLine($"Can parse 'aa': {canParse3}"); // Expected: True
        if (canParse3)
        {
            var parseTree3 = parser.GetParseTree(tokens3);
            Console.WriteLine($"Parse Tree 3: {parseTree3}");
            // Example output might look like: S(B(a), B(a))
        }
    }
}
```

## Detailed Explanation

### Data Structures:

*   **`CnfRule`**: A `struct` representing a single production rule. It stores the `NonTerminal` on the left-hand side and the `RightHandSide`. It includes properties to easily identify if it's a terminal rule (`A -> a`) or a binary non-terminal rule (`A -> BC`), and to extract the terminal or non-terminal symbols.
*   **`CnfGrammar`**: A class that encapsulates the grammar. It holds a collection of `CnfRule` objects and the `StartSymbol` of the grammar.
*   **`ParseTreeNode`**: A class representing a node in the parse tree. Leaf nodes represent terminals, while internal nodes represent non-terminals. Internal nodes have `Left` and `Right` children, corresponding to the two non-terminals in a CNF binary rule.

### `CykParser` Class:

1.  **Constructor**: Takes a `CnfGrammar` object. It initializes dictionaries (`_terminalProductions`, `_nonTerminalProductions`) to efficiently look up rules based on their right-hand sides. This indexing is done in `IndexProductions()`.
2.  **`IndexProductions()`**: Iterates through all grammar rules and categorizes them into terminal productions (keyed by the terminal symbol) and non-terminal productions (keyed by the two-non-terminal string, e.g., "AB").
3.  **`Parse(IReadOnlyList<string> tokens)`**: This method implements the core CYK algorithm:
    *   It initializes a 2D dynamic programming table, `dpTable`, of size `n x n`, where `n` is the number of tokens. Each cell `dpTable[i, j]` stores a `HashSet<string>` of non-terminals that can derive the substring of tokens starting at index `j` with length `i+1` (or `len` in the code, where `len` is `i`).
    *   **Initialization (Length 1 substrings)**: The first row (or `len = 0`) of the table is filled. For each token `tokens[j]`, it finds all rules `A -> tokens[j]` and adds `A` to `dpTable[0, j]`.
    *   **Table Filling (Length 2 to n substrings)**: The algorithm iterates through increasing substring lengths (`len` from 1 to `n-1`). For each length, it iterates through all possible starting positions `j`. For each substring `tokens[j...j+len]`, it considers all possible split points `k` (where `0 <= k < len`). The substring is split into `tokens[j...j+k]` and `tokens[j+k+1...j+len]`. It then checks if there's any rule `A -> BC` such that `B` can derive the first part (found in `dpTable[k, j]`) and `C` can derive the second part (found in `dpTable[len - 1 - k, j + k + 1]`). If such a rule exists, `A` is added to `dpTable[len, j]`.
    *   **Result**: The input string is accepted if the grammar's `StartSymbol` is present in the top-right cell of the table, `dpTable[n-1, 0]`, which represents the entire input string.
4.  **`GetParseTree(IReadOnlyList<string> tokens)`**: This method extends the `Parse` method to reconstruct the parse tree:
    *   It uses a similar DP table, but each cell `dpTable[i, j]` stores a `List<Tuple<string, ParseTreeNode?, ParseTreeNode?>>`. Each tuple represents a possible derivation for the substring `tokens[j...j+i]`, storing the non-terminal symbol and the constructed `ParseTreeNode` for that derivation.
    *   **Initialization**: For length 1 substrings, terminal rules `A -> a` create leaf `ParseTreeNode`s for the terminal `a` and store `(A, new ParseTreeNode(a), null)`.
    *   **Table Filling**: When a rule `A -> BC` is applied, and `B` is derived from `tokens[j...j+k]` with parse tree `leftNode`, and `C` is derived from `tokens[j+k+1...j+len]` with parse tree `rightNode`, a new `ParseTreeNode(A, leftNode, rightNode)` is created and stored along with `A` in `dpTable[len, j]`.
    *   **Result**: If the `StartSymbol` is found in the final cell `dpTable[n-1, 0]`, the corresponding `ParseTreeNode` is returned. Otherwise, `null` is returned.

## Complexity Analysis

Let `n` be the length of the input token sequence, `|V|` be the number of non-terminal symbols in the grammar, and `|R|` be the number of production rules.

*   **Time Complexity**: $O(n^3 \cdot |R|)$ or $O(n^3 \cdot |V|^3)$ depending on how rule lookups are implemented. With pre-indexed rules as done here, it's closer to $O(n^3 \cdot |V|^2)$ in the worst case for the `Parse` method, as we iterate through non-terminals derived from subproblems and check against rules. The `GetParseTree` method has the same asymptotic time complexity.
    *   The three nested loops for `len`, `j`, and `k` contribute $O(n^3)$.
    *   Inside the innermost loop, we iterate through possible non-terminals derived from the two subproblems. In the worst case, each subproblem could derive $O(|V|)$ non-terminals. Combining them leads to $O(|V|^2)$ pairs.
    *   For each pair, we look up rules. If the number of rules is $|R|$, the lookup might take $O(|R|)$ in a naive approach, but with pre-indexing, it's more efficient. If we consider the number of possible binary rules $A 	o BC$, it's $O(|V|^2)$. The total number of rules $|R|$ is often related to $|V|^2$. Thus, the complexity is often stated as $O(n^3 \cdot |V|^3)$ or $O(n^3 \cdot |R|)$.
*   **Space Complexity**: $O(n^2 \cdot |V|)$ for storing the dynamic programming table. Each of the $n^2$ cells can store up to $O(|V|)$ non-terminals (or parse tree nodes in the `GetParseTree` version). The `GetParseTree` version might use more space due to storing tree structures, but the asymptotic complexity remains dominated by the DP table.
